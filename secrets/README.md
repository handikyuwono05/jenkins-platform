# Runtime secrets

One secret per file, filename == secret name, value only (no `KEY=`, no
quotes, trailing newline is stripped). These are mounted read-only into the
container at `/run/secrets/<name>` and read by JCasC's `DockerSecretSource`,
which is why the YAML refers to them as `${google_oauth_client_id}` etc.

Everything in this directory except this file and `.gitkeep` is gitignored.

| File | Contents |
|---|---|
| `google_oauth_client_id` | OAuth 2.0 Client ID from Google Cloud (`...apps.googleusercontent.com`) |
| `google_oauth_client_secret` | OAuth 2.0 Client secret |
| `recovery_admin_password` | Break-glass local admin password; generated by `make init` |

Create them with `make init`, or by hand:

```bash
printf '%s' 'YOUR_CLIENT_ID' > secrets/google_oauth_client_id
printf '%s' 'YOUR_CLIENT_SECRET' > secrets/google_oauth_client_secret
chmod 600 secrets/*
```

Use `printf` rather than `echo` to avoid a trailing newline, and prefer a
leading space or `read -s` so the value does not land in your shell history.

## Beyond local development

Files on a developer laptop are an appropriate boundary for evaluation, not
for production. In production hold these in Google Secret Manager (or Vault)
and deliver them to the container at runtime — for example a CSI secrets
driver on GKE, or JCasC's Vault secret source. Rotate the OAuth client
secret on a schedule and immediately after any suspected exposure; rotation
here is a file replacement plus `make restart`.
